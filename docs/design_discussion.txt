what is the feasability of making a simplified version of clashroyale to run on a fpga board (Nexys A7 with the Artix100T) through VGA to a monitor.

Very feasible, as long as you scope it as “Clash Royale-style lane battler” rather than a faithful clone. The Nexys A7-100T is overkill for this.

Why the hardware is plenty

Artix-7 100T has ~63k LUTs, 135 BRAMs (about 4.8 Mb), and 240 DSP slices. A simple 2D game uses a small fraction of that.
VGA on the Nexys A7 is 12-bit color (4 bits per channel) through resistor ladders, which is fine for sprite art.
640x480@60Hz needs a 25.175 MHz pixel clock (25 MHz works on most monitors). Easy to generate with the MMCM.
The real constraint: framebuffer memory
A full 640x480 framebuffer at 12 bpp is ~3.7 Mb, which technically fits in BRAM but eats nearly all of it. Better options:

Render at 320x240 and pixel-double to 640x480. 320x240x12 = ~920 kb, which is comfortable. Even 4-bit indexed color with a palette drops it to ~300 kb.
Skip the framebuffer entirely and use a “racing the beam” design: for each pixel, combinatorially decide what color it is from tile map + sprite positions. This is the classic approach, and it’s how NES-era hardware worked. Very FPGA-native.
The Nexys A7 also has 128 MB DDR2, but driving it (MIG IP) adds a lot of complexity. You don’t need it.
What’s realistic to build

A tile-based arena (static background from a ROM/BRAM tile map: river, bridges, towers).
2 to 3 troop types with different speed/HP/damage, maybe 8 to 16 units on screen at once. Sprite rendering is a per-pixel comparator against each unit’s bounding box, so unit count scales with logic, not memory.
Two lanes, bridge crossing, simple target-nearest-tower or nearest-enemy AI.
Towers with HP bars, win condition when a king tower falls.
Elixir counter that ticks up, card buttons on the board’s switches/buttons to deploy.
Game logic updated once per frame (during vblank), so timing stays simple.
What’s hard or worth cutting

Pathfinding: skip A*. Use fixed lanes and “walk toward nearest target” with simple collision (or none).
Smooth physics and unit pushing: cut it.
Large sprite art: store sprites in BRAM as small indexed bitmaps (e.g. 16x16, 4-bit). You’ll need a script to convert PNGs to .coe/.mem files.
Input: 5 buttons + 16 switches is enough for deploying cards. A USB mouse (PS/2 emulation on the A7 USB-HID port) is doable but is a side project. Skip it initially.
Opponent: a simple LFSR-driven random spawner works fine as the “enemy.”
Architecture I’d suggest

VGA timing generator + MMCM (do this first, display a test pattern).
Tile/background renderer from BRAM ROM.
Sprite engine: unit table in registers, per-pixel overlap check, priority mux.
Game logic FSM or a small soft CPU (MicroBlaze or a tiny RISC-V). Pure RTL is fine for this scope, but a soft CPU makes game logic much faster to iterate on if you’re comfortable with the toolchain.
Input debounce, elixir/card logic, enemy spawner.
Audio is optional (the board has PWM audio out), so treat it as stretch.
Effort estimate

VGA test pattern to moving sprite: a weekend if you’ve done Verilog before.
Playable two-lane prototype with towers, 3 troops, and win/lose: roughly 3 to 6 weeks part-time, mostly spent on game logic and debugging timing, not on resource limits.
Full-fidelity Clash Royale (deck system, ~100 card behaviors, free-roam pathing, networking): not realistic, and not a good use of an FPGA.
Biggest risks

Too much combinational logic in the pixel path causing timing failures at the pixel clock. Pipeline the sprite lookups by a cycle or two.
Scope creep. Lock the feature list early.
Sprite art pipeline friction, so automate the PNG-to-memory conversion in Python early.

to control, we can use the switches and the button pad. use switch to deploy characters and enable p1 or p2 to use button pad

That scheme works well and costs almost nothing in logic. Here’s how I’d lay it out.

Split the roles: switches pick what, the pad picks where

Card switches: flipping one deploys that card at your cursor’s current position.
Button pad: moves your cursor (L/R picks the lane, U/D picks depth within your own half). BTNC can confirm or cycle something later if you want.
Pad owner switch: decides whose cursor the pad moves. Both cursors keep their position when you’re not the owner, so players can hand the pad back and forth.
Physical layout (matters on the Nexys A7)
SW0 is the rightmost switch and SW15 is the leftmost, so match the players to their sides:

P1 cards: SW[15:12] (left side)
P2 cards: SW[3:0] (right side)
Pad owner: SW[8] (0 = P1, 1 = P2), somewhere in the middle
The 5-button pad sits on the right side of the board, which is a bit unfair to P1, so the owner switch matters.
Use the LEDs above the switches to show who currently owns the pad.
If you’d rather have separate “enable P1” and “enable P2” switches, you can, but you have to define what happens when both are on or both are off. A single owner switch avoids that, so I’d start there.

Deploy logic

Run each switch through a 2-FF synchronizer, then a short debounce (a few ms is plenty).
Detect an edge on the synchronized switch, either direction, so flipping up or down both deploy. Rising-edge only is also fine, but then you have to flip it back down before reusing the card, which feels like a built-in cooldown.
On an edge, check elixir. If there isn’t enough, drop the request and spawn nothing.
Process at most one deploy per player per frame (latch the request and consume it in vblank). If two edges land in the same frame, just take them in priority order.
Edge-detect the buttons too, so a held button doesn’t scroll the cursor at 60 moves per second. Either move once per press, or add a slow repeat timer (about every 8 to 10 frames) when held.
Cursor rules

Clamp each cursor to its own half of the arena so nobody drops troops next to the enemy king tower.
Draw the cursor as a blinking box using the same sprite path as units, with a different palette.
The 7-segment display has 8 digits, so use 4 for each player’s elixir.
Gotchas

If P1 and P2 both flip a card in the same frame, it should just work if your spawn logic handles two requests per frame (a 2-entry queue is enough). Don’t let one player’s input starve the other.
Switches don’t tell you “intent” the way buttons do. If someone leaves a card switch up at power-on, you’ll get a phantom deploy. Initialize the edge detector to the current switch state at reset so it doesn’t fire.
A fixed 4-card hand per player is the simplest version. A rotating hand (like the real game) needs a small FIFO/shuffle, so save it for later.
Want me to write the input module (synchronizer, debounce, edge detect, cursor FSM) in Verilog? It’s small enough to do in one file and you can test it with just the LEDs before the VGA side exists.
